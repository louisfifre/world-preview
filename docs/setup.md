# How it works

What a run does, pass by pass, and what each file of the out folder leaves out. The README covers running it and lists the files.

## A run

The driver (`driver/`, the program `world-preview.exe` or the library `world_preview::run`) prepares a throwaway dedicated server in its work folder (`--dir`, `run\preview` by default) and starts it:

1. It checks `eula.txt` in the work folder first, before downloading anything there. Accepting the Minecraft EULA is the folder owner's decision; no script writes it.
2. It takes the mod's jar. Next to its sources, it builds it when they are newer (`mod\gradlew.bat build`, a JDK 25; the first build downloads Gradle and the game, a few minutes). A copy without the sources takes the jar as it is.
3. It downloads the Fabric server launcher, then fills the work folder with the mods, again only when they changed. From a packwiz pack, packwiz-installer reads `pack.toml` straight from the disk and installs the pack's server side, at the versions the pack names. From a game folder, the jars of `mods` and the `config` folder are copied, and the versions are those the mod is built for (`mod\gradle.properties`). Distant Horizons, when it is there, is taken out of the work folder only: it plays no part in the generator's answers and costs seconds at every start.
4. It writes the pack's `config/tectonic.json` into the work folder, with the values the run asked for, and a `server.properties` for a server nobody joins (local only, port 25599, one small world folder per seed, watchdog off since the sampling runs inside one tick).
5. It starts the server. The mod, dormant unless the server is started with `-Dworldpreview.out`, samples the generator once the server is up, writes the files and stops the server.

The server's output lands in `last-run.log` in the work folder, what Java wrote as errors in `last-run.errors.log`, and the same two for packwiz-installer under `last-sync`. The server and packwiz-installer run inside a Windows job object that ends them with the driver: if the driver is stopped or crashes mid-run, the server stops with it instead of running on alone. A caller that holds the driver as a library sets `Options::stop` instead: the driver kills the server and the run returns `STOPPED`.

The mod makes several passes, from coarse to full. The sketches first: one point in 16, then 4, then 2 of the full grid along each side, each kept when it leaves at least 128 points a side, without the aquifers, so close but not proven exact. Each replaces `coarse.json` and writes its points as `coarse-<step>-heights.bin` and `coarse-<step>-biomes.bin`; an interface can read `coarse.json` every second and draw a sketch when it is finer than the one on screen.

While it works, the mod rewrites `progress.json` every half second: the pass under way (`sketch`, `map`, or `extras` for the cuts, ores and structures that follow a full map), its step and how many of its tiles of 16 x 16 points are done. Its presence alone tells that the game has started. During the map's own pass, the mod also writes the points it has so far, once a second: `partial-heights.bin`, `partial-biomes.bin` (an index into every biome the generator can place, `0xFFFF` for a point not sampled yet), then `partial.json`. An interface can draw them over the last sketch, so the map fills in tile by tile. Their biomes are read tile by tile, where the map reads them row by row: a point where two biomes fit equally may differ until the map itself lands. Each file is written beside its place and moved there in one go, so a reader never sees half of one. Then the full grid (`preview.json`, `heights.bin`, `biomes.bin`): the ground height from `ChunkGenerator.getBaseHeight` (heightmap `OCEAN_FLOOR_WG`, so a sea bed shows its depth) and the surface biome from the biome source. No chunk is generated. `preview.json` also lists, as `possible`, every biome the biome source can place, each with whether it is tagged `c:is_underground`: an interface can count the biomes of the square against those that are not, and name the missing ones.

The detail (`--detail`) stops the run earlier: at 32 or 64 blocks, the sketch of that step is written as the map itself (`preview.json`, `heights.bin`, `biomes.bin`) and the run ends there, without what follows. So a coarser map has no aquifers in its heights, no cuts, no ore rules and no structures, and what needs them, level land told from one point to the next 16 blocks away among it, cannot be read from it. The structures would be exact at any detail, since they ask the generator's placement and not the grid, but they cost the same whatever the detail (about 3.5 s for 8192 blocks on the machine they were measured on, growing with the area), which is what a coarser map is meant to spare.

The mod writes how long its own work took (`timing.json`, from the first pass to the last file); the rest of the wait, the game's start and stop, does not grow with the area. So one run at a detail foretells the wait at that detail on any area, its work scaled with the area: measured once, a run of 8192 blocks at 32 blocks foretold 30 s for 16384 blocks, which took 25 s, and that one foretold 3 min 15 s for 65536 blocks, which had taken 3 min 26 s. The game's start alone moves by a few seconds from one run to the next.

Last come the cuts. Up to four cuts through the ground (`section.json`, `section-<n>.bin`): lines running west to east across the whole square, from its west edge to its east edge (`samples * step` blocks: 8192 for 512 points every 16 blocks, 32768 for 2048), drawn at random from the seed among the rows of the map, kept at least an eighth of the square apart, the ones that cross the most different ground kept (a height, some sea, some level land). Each cell of a cut, one per block from the bottom of the world to its top, is what the generator's density and aquifers give: rock, air, water or lava. Then the ore rules the server ended up with (`ores.json`): every placement of an ore feature with its steps, as a data pack writes them, and for each biome the placements it lists once every mod has added its own. Trouble in this last part is logged and leaves the map as it is.

Then where structures would start (`structures.json`): `structures` lists every structure of every structure set the overworld generator can place, as `{ "id", "set", "step" }` (the step is the generation step the structure declares, `surface_structures` or `underground_structures` for most), and `points` holds one row per start inside the square, `[index into structures, x, z]` in blocks. The mod asks the generator what it asks when a chunk reaches its structure starts, without any chunk: for each set, the chunks its placement picks (one per region of a random spread, or the stronghold rings), its frequency and its exclusion zone, then which structure of the set is tried there (a weighted draw seeded by the chunk, the next one drawn when the first is not valid) and whether that structure finds a valid point, its biome included. `/locate` is not used: it loads chunks. Its limits: a point is where a structure begins, at the generation point it found, not all it covers (a village spreads over several chunks around it); what a later step of a real chunk changes is not known; a point whose structure starts in a chunk of the square but lands just outside it is left out. Trouble here is logged apart from the cuts, so one never loses the other.

The engine places no ore: `ores.json` gives the rules, and an interface plays them on a cut, for each chunk along it, each rule its surface biome lists drawing its tries and its veins the way the game does. The ground of a cut is then the generator's, and its ores are a play of the rules, not the blocks a world of that seed would hold. Compared once with real chunks (a census of another world of the same pack, low ground), such a play gave about a fifth to a half more ore per chunk for the deep ores: its figures compare one try with another, they are not a count.

The computation leaves room for the rest of the machine: the mod samples on three quarters of the available processors (`-Dworldpreview.threads=<n>` on the server's command line says otherwise), and the driver puts the server below the normal priority. With every thread at the normal priority, a full pass made the machine stall for seconds at a time. Half was the rule before that priority; on 16 threads, 14 instead of 8 took a pass of 1024 x 1024 points from 40 s to 30 s, with the same files.

`--mod <jar>`, repeatable (or the environment variable `WORLD_PREVIEW_MODS`, paths separated by semicolons) adds jars to the server on top of the pack's, for a mod being worked on; those of the run before leave the folder first.

A changed Tectonic value applies on the next start, on the same world folder. Two runs never go together on one machine: they would share a port and, often, a folder. The second waits on a named mutex.

## The former page and its server

`page/preview.html` and `scripts/serve.ps1` are not the engine. They stay only because the page launcher of Outpost Tools still starts `serve.ps1 -NoWindow -ParentPid <its process>` and shows the page in a frame, on `http://localhost:25590`; they go once it stops. The server opens no window, runs `world-preview.exe` when the page asks (building it first when it is stale), serves the out folder's files under `/preview/data/<file>`, and stops when the parent process ends or once the page's pings stop. Inside the frame, the page tells its host where a run stands with `postMessage` (`{ source: 'world-preview', state }`) and sends its tabs (`{ source: 'world-preview', tabs }`); the host posts `{ source: 'host', tab }` back when one of them is clicked.
